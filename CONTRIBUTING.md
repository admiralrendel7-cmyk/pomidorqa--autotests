# Правила внесения изменений

Репозиторий — личный набор автотестов PomidorQA: unit, mock/live API и e2e на Playwright.

## Процесс

Изменения в `main` идут через отдельную ветку и Pull Request.

Префиксы веток:

- `test/` — новые или переработанные тесты;
- `fix/` — исправление падения или флака;
- `refactor/` — структура без смены поведения;
- `docs/` — документация;
- `chore/` — служебные правки.

## Окружение

```bash
git checkout main
git pull origin main
npm ci
npx playwright install chromium
```

## Проверки перед Pull Request

```bash
npm run lint
npm run test:unit
npm run test:api
npm run test:e2e
```

Или сразу `npm test`. Если e2e упал — не гоняйте его до случайного зелёного: сначала разберите причину.

Локально retries выключены. В CI — один worker, чтобы не перегружать общий стенд `https://aiqa.su`.

## Правила тестов

- сценарий и `expect` — в `tests/e2e`;
- локаторы и действия экрана — в `tests/pages`;
- пользователь и подготовка данных — в `tests/helpers`;
- регистрация через UI — только когда проверяется сама регистрация;
- в остальных сценариях аккаунт создаётся через тестовое API и удаляется в `finally`;
- данные уникальны на прогон;
- хост и гость живут в разных `BrowserContext`;
- без `waitForTimeout`, `force`, `.only`, `skip` и `page.pause()`.

Подробности — в [CODEX.md](CODEX.md), чек-лист ревью — в [REVIEW.md](REVIEW.md).

## Что писать в Pull Request

1. Что изменено?
2. Какой риск или требование из [`requirements.md`](requirements.md) закрывается?
3. Чем подтвердили: lint, unit, api, e2e?

Несвязанные правки не смешивайте. Если живой стенд ведёт себя иначе, чем требование, напишите это прямо — как с дефектом R8.3, а не прячьте `test.fail()` без пояснения.

## Документация
